# codegate

Шаблон настроек Claude Code, который задаёт жёсткий рабочий процесс разработки.
Рассчитан на команды, где junior–middle разработчики пишут код с помощью AI-агентов.

English version: [README.md](README.md).

## Что делает

Каждая задача проходит фиксированные фазы, пока код не попадёт в ревью:

0. **Старт** — задача = ветка: своя сессия, привязанная к этой ветке. Если в папке
   незаконченная работа, новая задача уходит в свой worktree.
1. **Elicitation** — агент сначала строит карту «кто читает и пишет данные задачи», потом
   спрашивает кругами, не больше четырёх вопросов за раз и с рекомендацией у каждого:
   архитектурные (как изменение встанет в систему, варианты, нет ли решения проще или шире)
   и бизнесовые никогда не в одном сообщении. Круги идут, пока не останется открытых вопросов;
   слишком большую задачу агент предлагает разбить. В конце — сводка решённого и того, что он
   решил сам.
   **Маленькая задача** всё это пропускает: ясна без вопросов, ничего дорогого в откате (нет
   новых таблиц, колонок, полей API, эндпоинтов), правка в одном месте, не задевает зоны,
   которые проект исключил (опция `short_path_excluded`; полные правила —
   `.claude/agents/elicitation/short-path.md`). Рефакторинг — на тех же условиях. Агент говорит об этом одной строкой
   с 1–3 критериями приёмки; пользователь подтверждает словом, и задача идёт тестом вперёд
   прямо в гейт, ревью и PR/MR. Оказалась больше — возвращается в elicitation.
   До первого архитектурного вопроса агент пишет черновик дизайна (`design.md`): форма
   решения, варианты по каждому решению и рост, который оно затрагивает. Рост взвешивается
   ценой, а не угадыванием вероятности: простое, если его дёшево дорастить потом; простое с
   открытой дверью, если запереть дорогу можно избежать почти бесплатно; вопрос
   пользователю — только когда это дорогая ставка на рост с источником. Критик, не видевший переписки, читает черновик и код: готовая реализация,
   путь проще, лишняя или недостающая расширяемость, риски, решения, оставленные
   исполнителю. Агент принимает, отклоняет или превращает каждое замечание в вопрос —
   пользователь выбирает из уже проверенных вариантов.
2. **Planning** — согласованный дизайн записывается как файлы, тесты и коммиты; своих
   дизайн-решений планировщик не принимает, а открытые возвращает вопросом. Затем
   детерминированный скрипт проверяет, что все упомянутые пути, символы и версии миграций
   существуют, и предупреждает, если файл, который план собирается создать, уже носит имя
   существующего символа.
3. **Implementation** — реализация по утверждённому плану, кусками, тест первым; каждый кусок
   делает суб-агент по файлам сессии.
4. **Quality gate** — сначала механика, командами: полный прогон тестов, покрытие (каждая
   новая осмысленная строка продового кода должна быть покрыта тестом), ассерты (тест,
   которого коснулся дифф, обязан утверждать что-то, что может упасть — покрытие доказывает,
   что строка выполнилась, а не что кто-то заметил бы её ошибку), линтеры проекта в режиме
   проверки и проверки проекта из опции `gate_checks`. Затем гейт судит результат по одному
   списку правил: один агент проходит его целиком или (опция `gate_mode=lenses`) три линзы —
   архитектура, безопасность, тесты — берут свои разделы. Читает файлы целиком, а не только
   дифф, с учётом baseline тестов и tech-debt. В конце — независимое ревью: субагент видит
   только задачу и код, без плана и рассуждений автора.
5. **PR creation** — PR/MR с отчётом качества; связанные задачи в трекере для проектов-
   потребителей (другой сервис, приложение) — после того как пользователь подтвердит черновики.
6. **После PR/MR** — находки QA, замечания ревью и правки CI — это *доработка*: та же ветка,
   перед пушем проверяются только новые коммиты. Дефект после мержа или расширение —
   новая задача, связанная с исходной.

В `CLAUDE.md` — только ядро (~6 тыс. символов); шаги каждой фазы — скилл
(`.claude/skills/cg-phase-N`), который подгружается при входе в фазу, а не уходит в каждый
вызов модели и каждому суб-агенту.

Хуки блокируют вызовы `Write` и `Edit` агента на неправильной фазе. Записи
через Bash (редиректы, `sed -i`) не перехватываются — это страховка, а не
песочница.

## Установка

Скопируйте в корень вашего проекта:

```
CLAUDE.md
.claude/
```

Установка сама добавляет в `.gitignore` (данные сессий живут только на машине; контекст кода
хранится в git, tech-debt — по настройке `tech_debt_in_git`):

```
.ai/sessions/
.ai/current-session
.claude/worktrees/
```

Сессии ещё копируются в git-каталог репозитория (`.git/codegate/sessions/`), общий для
всех worktree, — удаление worktree не теряет его задачу.

Python 3 обязателен: хуки разбирают им каждый вызов. Без него блокируются любые Write/Edit,
пуши и создание PR/MR (на Linux/Mac он стоит, на Windows его надо поставить).

## Использование

### Первый запуск в проекте

```
/cg-context
```

Анализирует проект, создаёт `.ai/CODEBASE_CONTEXT.md`, логирует существующие
проблемы в `.ai/tech-debt/`. Коммитьте `CODEBASE_CONTEXT.md`, чтобы у команды
был общий baseline.

### Начало задачи

```
/cg-feature  добавь фильтр по дате на страницу результатов
/cg-bugfix   пользователи не могут войти после сброса пароля
/cg-refactor вынеси логику экспорта в отдельный модуль
```

Ответьте на вопросы фазы elicitation — дальше фазы идут сами.

### Когда процесс останавливается

Режим один: между фазами ничего подтверждать не нужно. Остановка — только за тем, что может
дать лишь пользователь: круг вопросов elicitation, вопрос о поведении или объёме во время
реализации, FAIL гейта, который не удалось исправить за три раунда, находка без права
override. Артефакты (план, отчёт гейта) по дороге всё равно показываются.

```
/cg-approve quality   # принять FAIL-пункты, которые гейт не смог исправить
/ok                   # «да, дальше»: принять рекомендации круга; FAIL не переопределяет
```

### Прочие команды

```
/cg-status   # задача этой ветки: состояние и следующий шаг
/cg-tasks    # все задачи репозитория: ветка, состояние, worktree
/cg-merged  # влит ли PR/MR задачи; если влит — закрывает задачу
/cg-next     # задачи из трекера, назначенные на вас, и какие из них уже начаты
/cg-debt     # список записанных tech-debt
/cg-resume   # продолжить задачу этой ветки после /clear, компакции или нового окна
```

### Трекер задач

Codegate не знает ни одного трекера. Он просит абстрактные действия — создать (в том числе в
другом проекте, со связью и ссылкой), получить, событие (`started`, `pr_created`, `merged`),
комментарий, связь, «мои задачи» — через `.claude/scripts/tracker.py` (договор в описании
скрипта). Отвечает на них адаптер проекта, в одном или двух видах: `.claude/tracker-adapter.py`
— скрипт; `.claude/tracker.md` — инструкция, как сделать действие инструментами, которые у ИИ
пользователя уже есть для этого трекера (MCP-сервер, CLI). Что скрипт не умеет, передаётся
агенту с этой инструкцией или пропускается. Настройки и ключи остаются у проекта. `/cg-start`
спрашивает, подключать ли трекер (`tracker`: `none` или `adapter`) и какие проекты потребляют
этот (`consumers`). Ещё он спрашивает, как запускается полный набор тестов (`test_command`):
процесс гоняет его до первой строки кода и в гейте качества; проекту, которому для этого
нужен свой скрипт, это задаётся здесь. Если в проекте PR/MR открывают по-своему (обязательные
флаги, push-опции), команду для этого задают в `pr_command`. Задача руками — `/cg-tracker`, назначенное на вас — `/cg-next`.

## Структура после установки

```
your-project/
├── CLAUDE.md                          # инструкции процесса (единственный источник правды)
├── .claude/
│   ├── settings.json                  # хуки + запреты
│   ├── hooks/
│   │   ├── pre-write.sh               # блок записи файлов до утверждения плана
│   │   ├── pre-push.sh                # блок git push до прохождения quality gate
│   │   ├── pre-agent.sh               # без задачи на ветке нет элицитации и плана
│   │   ├── task-context.sh            # к каждому сообщению — задача ветки и её состояние
│   │   ├── post-stop.sh               # копирует сессии в общее хранилище
│   │   └── post-compact.sh            # где стоит задача — на старте и после компакции
│   ├── skills/                        # cg-phase-0…5, cg-rework, cg-flow-feedback
│   ├── commands/                      # слэш-команды (cg-*)
│   ├── scripts/
│   │   ├── cg_session.py              # какая задача у этой рабочей копии; общее хранилище
│   │   ├── cg_cmd.py                  # что запускает Bash-вызов: пуши и создание PR/MR, для хуков
│   │   ├── tracker.py                 # мост к трекеру (действия → адаптер проекта)
│   │   ├── plan-integrity.py          # проверка путей/символов/миграций (Фаза 2)
│   │   ├── test-assertions.py         # проверка «тест хоть что-то утверждает» (Фаза 4)
│   │   └── diff-coverage.py           # проверка покрытия (Фаза 4)
│   └── agents/                        # промпты суб-агентов
│                                      # (собственные тесты cg-core лежат в
│                                      #  core/tests/ и в проект НЕ ставятся)
│       ├── codebase-intelligence/     # /cg-context
│       ├── elicitation/               # Фаза 1 (включая триаж косметики)
│       ├── planning/                  # Фаза 2
│       ├── implementer/               # Фаза 3, один кусок плана, тест первым
│       ├── design-critic/             # Фаза 1, свежий взгляд на черновик дизайна
│       ├── quality-gate/              # Фаза 4
│       ├── independent-review/        # Фаза 4, последний шаг: видит только задачу и код
│       └── pr-creator/                # Фаза 5
└── .ai/                               # runtime-состояние
    ├── CODEBASE_CONTEXT.md            # коммитить
    ├── tech-debt/                     # в git, если tech_debt_in_git не no
    └── sessions/                      # gitignored — эфемерные
```

## Требования

- Claude Code CLI
- Python 3 — обязателен: без него хуки блокируют запись и пуши (стандартен на Linux/Mac)
- `git`
- `gh` или `glab` — опционально; без них создание PR вернёт ссылку для ручного оформления
